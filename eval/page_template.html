MoBot: Visual Navigation and Docking with an EKF and LQR

Anne (26202693) & Vishnu (26224699)

Code on GitHub · Run in Colab · Demo video

Summary

A simulated TurtleBot3 Burger in MuJoCo[3] crosses a room with obstacles, finds a charging dock marked with an ArUco tag, and parks 0.35 m in front of it. An EKF fuses wheel odometry and the gyro with the tag's pose from the camera, and an LQR controller steers on that estimate. The controller never uses the simulator's true pose; ground truth is used only to score the runs (src/judge.py, eval/).

Model

Unicycle kinematics, state [x, y, θ], input [v, ω]:  ẋ = v cosθ, ẏ = v sinθ, θ̇ = ω, with v = r(ωR+ωL)/2 and ω = r(ωR−ωL)/b. Wheel radius r = 0.033 m and separation b = 0.160 m[2]; speed limits 0.22 m/s and 2.84 rad/s[1]. Assumed: flat floor, no wheel slip. Slip does happen when turning on the spot, so the EKF takes rotation from the gyro.

For the controller, the model is linearised about a straight reference line at speed v (ey = sideways error, eθ = heading error): ė = [[0, v], [0, 0]] e + [[0], [1]] ω.

Frames

Camera (OpenCV: x right, y down, z forward) → robot base (ahead = 0.04 + z, left = −x) → dock frame, where the EKF's state lives → the controller's sideways and heading errors. The EKF runs in the start frame until the tag is first seen.

Sensing

  • Camera calibration with a 9×6 checkerboard at 40 poses, using Zhang's method[4]: RMS reprojection error 0.06 px; focal length within 0.02% of the simulator's value (models/camera_calibration.json).
  • Tag pose from the four corners with OpenCV's solvePnP, IPPE-square method[5].
  • Measured noise at 400 known poses (0.4–3.6 m). The camera reads distance too long by 0.0075·d² (+7 cm at 3 m), which we subtract. The remaining spread, σ(d) = a + b·d², sets the EKF's R. 4% of angle readings were off by more than 15°, and the EKF rejects them.

Estimation: EKF

  • State [x, y, θ] with covariance P. Predict at 20 Hz from the encoders (distance) and the gyro (rotation). Q is from odometry errors measured over 3,778 steps (models/odometry_noise.json).
  • Update at up to 5 Hz from the tag pose, with R(d) from the noise model above. Readings with a Mahalanobis distance above 11.34 (the 99% χ² value for 3 degrees of freedom[8]) are rejected; 6 rejections in a row trigger a re-fix from the tag.
  • Tuning: with the measured Q and R, NEES (which should average 3 for a consistent 3-state filter[7]) was about 30, because the errors are correlated from step to step. A sweep of 12 settings chose Q × 4, R × 16: NEES __TUNE_NEES__ and __TUNE_NEAR__ cm estimate error near the dock.

Control: planner and LQR

Planner: search (spin) → explore (LiDAR picks an open, unvisited spot) → approach a point 0.8 m in front of the dock → align → dock along the centre line → square-up (turn on the spot to within 1°). Obstacles: a 0.4 m wide, 0.7 m long corridor ahead is checked in the LiDAR scan; if blocked, the robot steers to the nearest clear direction.

LQR on the EKF estimate: ω = −K(v)·[ey, eθ]. Weights by Bryson's rule[6]: Q = diag(1/0.05², 1/(10°)²), R = 1/(1 rad/s)². K is recomputed for the current speed (gain scheduling); the turn rate is capped at 1.5 rad/s.
